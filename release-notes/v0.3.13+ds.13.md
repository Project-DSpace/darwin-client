## What changes

This release fixes a fault in how the client sends a payment: it could send a second transaction for a payment it had already made. No DARWIN was ever paid twice, because both vaults refuse to record the same payment again, but the second transaction cost gas and the upload reported the wrong transaction and a cost of zero. Everything else is as in v0.3.13+ds.12.

### What was seen

On 2026-11-14 the first paid test upload made with v0.3.13+ds.12 (1,024 bytes, four records paid as one root wave) sent two transactions to the root vault one second apart. The first recorded the wave and moved 0.5009 DARWIN. The second carried the same payment, recorded nothing and moved no tokens, so it cost only its gas. The upload stored and verified, and its record names the first transaction, but the client reported the second one as its payment with a storage cost of `0`. Earlier releases from v0.3.11+ds.1 on have the same fault; it shows only when the RPC loses the answer to a send.

### The cause

When an answer to a send is lost (a timeout, a rate limit or a dropped connection), the wallet library sends the same signed transaction again and returns only the last answer. If the chain had in fact taken the first send, the second is refused with "nonce too low", because the transaction already used that nonce. The client took that refusal as proof that the transaction had never left it, so it signed the payment again with a new nonce and sent it a second time.

### What a user could lose

Gas, never tokens. On the root vault a wave already recorded is not recorded again and moves nothing; on the per-quote vault a quote already paid is skipped. But the second transaction's gas was spent, the upload reported its cost as zero (root vault) or named a transaction that paid nothing (per-quote vault), and, had signing the second one failed, the upload's checkpoint would no longer have held the transaction that paid.

### What the client does now

- **It looks for the refused transaction on the chain first.** When a payment's first send is refused for its nonce, the client reads the chain for that exact signed transaction up to three times, one second apart. If it was mined, it is the payment, with its own cost and transaction, and nothing is signed again.
- **It checks the vault before it would sign again.** If those three reads don't find it, the client reads the vault before signing anything: the root vault's record of the wave, or the per-quote vault's records of the quotes, for single payments and for small files sharing a wave alike. If the vault shows the payment, nothing is signed. The client finds the transaction that recorded it by the vault's log, again in up to three reads one second apart, and reports that transaction and its cost when this wallet sent it.
- **It never reports a cost it doesn't know.** If the vault shows the payment but the transaction that recorded it, and so its cost, can't be found or read in those reads, the upload stops with an error saying the cost isn't known yet, rather than reporting zero. If a read of the chain or the vault fails, it stops the same way. In both cases the checkpoint keeps the signed transaction, and the next attempt checks the chain again, sending nothing new until it knows how that transaction ended.
- **A root wave recorded by this wallet's earlier transaction is counted.** If a second transaction was still sent (the chain's replicas lagging past all of the reads above), the upload reports the wave's total as paid, by the transaction that recorded it, with both transactions' gas, rather than a cost of zero.
- **A real stale nonce is unchanged.** A payment signed with a nonce the chain had already used, and never mined, is still signed again with a fresh nonce, after the reads above find nothing.

### Known limits

- Token approvals, which the wallet library sends when the vault's allowance is short (once per wallet and vault), and the library payment functions the `darwin` command never calls (`Client::batch_pay`, `Client::pay_for_merkle_batch`, the single-record payment of builds without the `native` feature, and the upload adapter's own `pay` and `pay_merkle`) still go through the library's older send, which can sign again after a send timeout: at the cost of gas only, except a batch (merkle) payment sent again, which the vault can charge twice and which the `darwin` command refuses.
- Batch (merkle) payments through the upload engine get the chain reads above but no vault check before they are signed again.

## Releases

- **It is tested against darwin-node 0.24.0+ds.22**, the revision its tests pin, as v0.3.13+ds.12 is.
- **This release is published only after** the tagged commit's Test run and its Build run on `main` both passed.
- **Going back** to v0.3.13+ds.12 is a binary swap under the usual pause; that version has the fault this one fixes.
