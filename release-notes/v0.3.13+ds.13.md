## What changes

This release fixes a fault in how the client sends a payment: it could send a second transaction for a payment it had already made. The vaults never record the same payment twice, so the second transaction itself moved no tokens, but it cost gas, the upload reported the wrong transaction and a cost of zero, and on the per-quote vault it could lead to a record being paid for again (below). Everything else is as in v0.3.13+ds.12.

### What was seen

On 2026-11-14 the first paid test upload made with v0.3.13+ds.12 (1,024 bytes, four records paid as one root wave) sent two transactions to the root vault one second apart. The first recorded the wave and moved 0.5009 DARWIN. The second carried the same payment, recorded nothing and moved no tokens, so it cost only its gas. The upload stored and verified, and its record names the first transaction, but the client reported the second one as its payment with a storage cost of `0`. Earlier releases from v0.3.11+ds.1 on have the same fault; it shows only when the RPC loses the answer to a send.

### The cause

When an answer to a send is lost (a timeout, a rate limit or a dropped connection), the wallet library sends the same signed transaction again and returns only the last answer. If the chain had in fact taken the first send, the second is refused with "nonce too low", because the transaction already used that nonce. The client took that refusal as proof that the transaction had never left it, so it signed the payment again with a new nonce and sent it a second time.

### What a user could lose

- **On the root vault: gas only.** The vault records a wave once, so the second transaction moved no tokens, and the records named the transaction that recorded the wave, so storers accepted them. The second transaction's gas was spent, and the upload reported a cost of zero.
- **On the per-quote vault: gas, and possibly tokens for a record paid again.** The vault skips a quote it has already recorded, so the second transaction moved no tokens itself. But the records named the second transaction, which holds no payment log. For an envelope, storers look for the payment only in the transaction its proof names, so they refuse that proof, and a later run of the same upload quotes that record again and pays for it again. We traced this by reading the code; it hasn't been seen.
- **On either vault, after a failed second signing.** Had signing the second transaction failed, the upload's checkpoint would no longer have held the transaction that paid, and a later run whose quotes had expired would have paid again.

With this release, the `darwin` command's per-chunk payments can't pay twice through this fault: the client no longer signs a payment again without first reading the chain and the vault for it, and a record made after a payment was sent again, or confirmed from an earlier run's checkpoint, names the transaction whose payment log shows its quote, never one the client hasn't seen record it. One older case remains, which this release doesn't change: if another wallet already recorded one of a payment's quotes in full, to that quote's own rewards address, before the payment, the record still names this payment's transaction, as in every release before; an envelope's proof is then refused and a later run pays that record again. Only someone who knew the quote before it was paid can do that, and it costs them the quote's full price. The library payment functions the `darwin` command never calls are listed under known limits.

### What the client does now

- **It looks for the refused transaction on the chain first.** When a payment's first send is refused for its nonce, the client reads the chain for that exact signed transaction up to three times, one second apart. If it was mined, it is the payment, with its own cost and transaction, and nothing is signed again.
- **It checks the vault before it would sign again.** If those reads don't find it, the client reads the vault before signing anything: the root vault's record of the wave, or the per-quote vault's records of the quotes, for single payments and for small files sharing a wave alike. If the vault shows nothing, the payment is signed again, as a payment refused for a stale nonce always was. If the vault shows the payment, nothing is signed: the client looks for the transaction that recorded it by the vault's log (by the wave's key, or by the payment's first quote), up to three times one second apart, and if this wallet sent it, that transaction is the payment, reported with its own cost.
- **Records after a second send, or from a checkpoint, are checked.** A per-quote payment confirmed after it was sent again, or confirmed from an earlier run's checkpoint, is checked against its transaction's own payment logs. For a quote those logs don't show, the client reads the vault's record again while it reads empty, up to three reads one second apart; if the record is that quote's payment, the record names the transaction whose log shows it, and that transaction's gas is added when this wallet sent it. A record that isn't the quote's payment (another address, or short) goes to the occupied-quote check, which quotes it again, as on every path. A root wave's records always name the transaction whose log shows the wave; a root wave sent again is reported as paid once, by that transaction, with both transactions' gas.
- **A reverted root wave recorded by another.** When a root wave's own transaction reverted while the root vault records the wave by another wallet's transaction, the reverted transaction's gas is now read and reported. Every other reverted payment ends as before, "payment reverted on-chain; retry is safe", with no cost reported.
- **Where the cost isn't known, the upload stops.** If the vault can't be read, or shows the payment recorded by another wallet after a refused send, or a record stays empty, or the transaction that recorded a payment, its sender or its gas can't be found or read within those reads, the upload stops instead of reporting a cost it doesn't know or a record it hasn't seen. Its error says the cost isn't known yet: **run the same upload again; nothing is paid twice.** The checkpoint keeps the signed transaction, and the next run looks it up on the chain before anything else and sends nothing new until it knows how that transaction ended.

The vault check searches for the recording at most three times, one second apart, each search held to the caps the root-wave search already had (at most 64 log queries). The record check after a second send, or on a resumed payment, searches once for each quote its transaction's logs don't show, up to three times each.

These checks are also reached without a lost answer, on paths that read nothing before: any per-quote payment or shared wave resumed from a checkpoint is checked against its transaction's logs; a root wave recorded by a transaction other than its own has that transaction's sender (and its gas, when it is this wallet's) read; and a reverted root wave recorded by another has its gas read. Each can now stop, with the checkpoint kept, where it used to report a cost of zero.

### Known limits

- **A payment confirmed on a later run isn't in that run's reported cost.** An upload's reported cost (`storage_cost_atto`, `gas_cost_wei`) counts only what that run paid. A payment made on an earlier run and confirmed on a later one, after one of the stops above or an interrupted upload, is counted in neither run's report; its transaction is named in the upload's record, and its cost can be read from the chain by that transaction.
- **Waiting for finality.** A payment signed with a stale nonce, which used to be signed again at once, now waits instead when the vault can't be read at that moment, or when another wallet has already recorded one of its quotes. The upload stops, and the next runs each end after up to 30 seconds with "payment outcome pending" until the chain finalizes the block that used the nonce: about a quarter of an hour on Robinhood Chain (the finalized block was about 17 minutes behind the latest when measured on 2026-11-14). On the per-quote vault, the first run after that ends once with "payment nonce was finalized …; retry is safe", and the run after it goes on. Nothing is paid twice.
- **A resumed upload that can't finish.** If a node recorded one of its own quotes in full, to its own address, more than an hour before the quotes' timestamps, and the upload was interrupted after paying, every resumed run stops with "its cost isn't known yet", because the record check can't find that recording. This needs a node acting on purpose. To get out, delete the upload's checkpoint and upload the file again; that pays again for the records of the payment it held.
- **Old history.** A checkpoint whose transaction has no receipt, once the RPC no longer serves the old blocks that would show which transaction used its nonce, stops with a message naming the transaction: if a block explorer shows it was never mined, nothing was paid and deleting the checkpoint is safe.
- **Time.** The record check on a large per-quote payment (up to 64 records) can take most of a minute, at the reader's pace of 10 calls a second.
- **Older send path.** Token approvals, which the wallet library sends when the vault's allowance is short (once per wallet and vault), and the library payment functions the `darwin` command never calls (`Client::batch_pay`, `Client::pay_for_merkle_batch`, the single-record payment of builds without the `native` feature, and the upload adapter's own `pay` and `pay_merkle`) still go through the library's older send, which can sign again after a send timeout. For an approval that costs gas only. For those payment functions it costs gas, and on the per-quote vault the record can name the transaction that paid nothing, with the consequence described above; a batch (merkle) payment sent again can be charged twice. The `darwin` command refuses batch payments.
- **Batch payments through the upload engine** get the chain reads above but no vault check before they are signed again.

## Releases

- **It is tested against darwin-node 0.24.0+ds.22**, the revision its tests pin, as v0.3.13+ds.12 is.
