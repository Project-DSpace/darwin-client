## What changes

This release fixes a fault in how the client sends a payment: it could send a second transaction for a payment it had already made. No DARWIN was ever paid twice, because both vaults refuse to record the same payment again, but the second transaction cost gas and the upload reported the wrong transaction and a cost of zero. Everything else is as in v0.3.13+ds.12.

### What was seen

On 2026-11-14 the first paid test upload made with v0.3.13+ds.12 (1,024 bytes, four records paid as one root wave) sent two transactions to the root vault one second apart. The first recorded the wave and moved 0.5009 DARWIN. The second carried the same payment, recorded nothing and moved no tokens, so it cost only its gas. The upload stored and verified, and its record names the first transaction, but the client reported the second one as its payment with a storage cost of `0`. Earlier releases from v0.3.11+ds.1 on have the same fault; it shows only when the RPC loses the answer to a send.

### The cause

When an answer to a send is lost (a timeout, a rate limit or a dropped connection), the wallet library sends the same signed transaction again and returns only the last answer. If the chain had in fact taken the first send, the second is refused with "nonce too low", because the transaction already used that nonce. The client took that refusal as proof that the transaction had never left it, so it signed the payment again with a new nonce and sent it a second time.

### What a user could lose

Gas, never tokens. On the root vault a wave already recorded is not recorded again and moves nothing; on the per-quote vault a quote already paid is skipped. But the second transaction's gas was spent, the upload reported its cost as zero (root vault) or named a transaction that paid nothing (per-quote vault), and, had signing the second one failed, the upload's checkpoint would no longer have held the transaction that paid.

### What the client does now

- **It looks for the refused transaction on the chain first.** When a payment's first send is refused for its nonce, the client reads the chain for that exact signed transaction up to three times, one second apart. If it was mined, it is the payment, with its own cost and transaction, and nothing is signed again.
- **It checks the vault before it would sign again.** If those reads don't find it, the client reads the vault before signing anything: the root vault's record of the wave, or the per-quote vault's records of the quotes, for single payments and for small files sharing a wave alike. If the vault shows nothing, the payment is signed again, as a payment refused for a stale nonce always was. If the vault shows the payment, nothing is signed: the client looks for the transaction that recorded it by the vault's log, up to three times one second apart, and if this wallet sent it, that transaction is the payment, reported with its own cost.
- **Every record names the transaction that recorded its payment.** A per-quote payment confirmed after it was sent again, or confirmed from the checkpoint of an earlier run, is checked against its transaction's own payment logs; a quote that transaction didn't pay is recorded under the transaction whose log shows its payment, and that transaction's gas is added when this wallet sent it. A root wave sent again is reported as paid once, by the transaction that recorded it, with both transactions' gas. A transaction that reverted after a lost answer has its gas reported.
- **Where the cost isn't known, the upload stops.** If the vault can't be read, or shows the payment recorded by another wallet, or the transaction that recorded it, its sender or its gas can't be found or read within those reads, the upload stops instead of reporting a cost it doesn't know. Its error says the cost isn't known yet: **run the same upload again; nothing is paid twice.** The checkpoint keeps the signed transaction, and the next run looks it up on the chain before anything else and sends nothing new until it knows how that transaction ended. While the chain hasn't settled it (for example, a transaction that was never mined, until the block that used its nonce is final), the next runs end with "payment outcome pending"; keep the checkpoint and run the upload again later.

The bound on all of this is three reads, one second apart, for each thing the client looks for (the transaction itself, and the transaction that recorded the payment); each search of the vault's logs is held to the caps the root-wave search already had, at most 64 log queries. A refused send whose logs lag as well therefore stops after three searches, not after searching every quote.

### Known limits

- **A payment confirmed on a later run isn't in that run's reported cost.** An upload's reported cost (`storage_cost_atto`, `gas_cost_wei`) counts only what that run paid. A payment made on an earlier run and confirmed on a later one, after one of the stops above or an interrupted upload, is counted in neither run's report; its transaction is named in the upload's record (`darwin file verify` shows it), and its cost can be read from the chain by that transaction.
- **Rare delays.** A payment signed with a stale nonce, which used to be signed again at once, now waits instead when the vault can't be read at that moment, or when another wallet has already recorded one of its quotes: the upload stops, and the next runs end with "payment outcome pending" until the chain finalizes the block that used the nonce, then the upload goes on. Nothing is paid twice in either.
- **Older send path.** Token approvals, which the wallet library sends when the vault's allowance is short (once per wallet and vault), and the library payment functions the `darwin` command never calls (`Client::batch_pay`, `Client::pay_for_merkle_batch`, the single-record payment of builds without the `native` feature, and the upload adapter's own `pay` and `pay_merkle`) still go through the library's older send, which can sign again after a send timeout. That costs gas only, except a batch (merkle) payment sent again, which the vault can charge twice; the `darwin` command refuses batch payments.
- **Batch payments through the upload engine** get the chain reads above but no vault check before they are signed again.

## Releases

- **It is tested against darwin-node 0.24.0+ds.22**, the revision its tests pin, as v0.3.13+ds.12 is.
- **This release is published only after** the tagged commit's Test run and its Build run on `main` both passed.
