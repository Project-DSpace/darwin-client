## What changes

This release is the root switch: the darwin CLI now pays through the root vault, DarwinRootVault at `0xf6675722f443132b045857546E57e35360Bb03b9` on Robinhood Chain, by default, and an outside payer (`UploadPayer`) can ask to pay root waves too. The library's default stays today's payment vault, `0xE0f627986c0438De0E314B644f3C8aA21D3f4f6B`. How root payments work, their proofs, the split between both vaults and the envelope rules are those of v0.3.11+ds.6. Prices are those of v0.3.11+ds.5: quotes on either price curve are accepted.

### CLI users: root by default

- **Every paying command pays through the root vault** unless told otherwise: each payment's records as one wave in one transaction, which the vault records once, and each record's proof (tag 0x03) showing its place in the wave.
- **`--no-root-payments`** pays through the payment vault only, as v0.3.11+ds.6 did without a flag. `--root-payments`, the opt-in of v0.3.11+ds.6, still parses (hidden from the help) so commands written for it keep running; it asks for the default, and it can't be given with `--no-root-payments`. Commands that don't pay no longer refuse it.
- **Falling back, record by record.** A record whose close group holds a node that can't check a root proof is quoted again for the payment vault and paid there, as in v0.3.11+ds.6. A payment pays both vaults only when at least 3 of its records pay the root vault; with fewer, they all pay the payment vault. The envelope never pays alone in either payment where moving records can avoid it, and records kept from an interrupted attempt never move.
- **On a devnet** (`--evm-network local`), the CLI reads and pays the root vault the devnet's manifest names (`evm.root_vault_address`). A manifest that names none leaves the CLI paying the payment vault, with a warning, instead of stopping. A manifest that names its own payment vault (`evm.payment_vault_address`) as its root vault is refused. On a devnet, `darwin listings`, `darwin listing` and `darwin file verify` still read the payment vault alone, so they don't see root-paid records there; on the bundled network they read both vaults, as since v0.3.11+ds.3.
- **Checkpoints.** An upload checkpoint holding a root plan or proof is written in the second format of v0.3.11+ds.6, which v0.3.11+ds.5 and older clients refuse. With root payments the default, an interrupted CLI upload that planned a root payment writes it. A journaled root payment is reconciled only by a client paying the root vault, so resume an interrupted upload without `--no-root-payments`.

### Library users: opt in, now in one call

- **The default stays the payment vault.** A `Client` pays through the root vault only once it opts in: `Client::with_root_payments` takes a root vault's wallet as before, and the new `Client::with_root_payments_from_key(network, private_key, chain_id)` sets the client's wallet and its root vault's wallet from one key in one call. It pays the bundled network's root vault, or the one the client names, and is refused when no root vault is known.
- **Naming a root vault without paying it.** `Client::with_root_vault(address)` names the root vault a client reads (`Client::root_vault` returns it): its envelope records and its read-backs of payments read that vault beside the payment vault, with no root vault's wallet needed. On the bundled network its built-in vault is read either way. On a devnet, `ant_core::config::manifest_root_vault` reads the vault a manifest names, and `ListingChain::new_with_root_vault(network, root_vault)` builds a reader of both vaults; `ListingChain::new` is that reader naming none.
- **The payment vault is never a root vault.** Once a client's payment network is known (`with_wallet` or `with_evm_network`), `with_root_vault` given that network's payment vault leaves the client as it was, with a warning. A root vault named before the network is known is dropped, with a warning, when `with_wallet` or `with_evm_network` sets a network whose payment vault it is. `manifest_root_vault` returns an error for a manifest whose root vault is its payment vault.

### Outside payers: root waves when asked

- **`UploadPayer::pays_root_waves`** (false by default). A payer that returns true is quoted for the root vault wherever every quoter of a record accepts root proofs and the client knows its network's root vault, built in or named with `with_root_vault`; no root vault's wallet is needed in the client. Its other records come in plans for the payment vault, in a payment of their own. A payer that doesn't ask is quoted for the payment vault alone, as before.
- **Paying a wave.** Each call to `pay_quotes` holds plans for one vault (`ChunkPaymentPlan::vault`). For the root vault, the payer sends one `payForQuotes` call to the root vault with the non-zero quotes' leaves in ascending quote-hash order, and returns the transaction for every paid quote and the plans' total. Asked again for a payment it already made, after a restart or an error, it returns that payment and sends nothing.
- **What the client does next.** It reads the root vault's record of the wave, finds the transaction that recorded it, and builds each record's proof naming that transaction. That is the payer's own when its receipt shows the recording; otherwise the vault's `RootPaid` log names it, also when the transaction the payer returned never gets a receipt, as when the payer's wallet sped it up or replaced it, or reverted and a later transaction recorded the wave. A wave recorded by another transaction is taken as paid by that one, and nothing is paid again. When that transaction was sent from the same address as the one the payer returned (its wallet's replacement), the upload's cost counts the wave's total; when it was sent from another address, or the senders can't be read, the payment counts as moving no tokens. A root request the payer paid at the payment vault instead is stored with single-node proofs (tag 0x01) once that vault records every quote. Where neither vault shows the payment, the upload stops with the payment kept pending, and the next attempt asks the payer again.
- **`UploadPayer::exact_approvals`** (true by default) says the payer approves each vault for exactly what it pays, so paying both vaults in one upload costs a second approval: its payments then pay both vaults only from 5 records that can pay the root vault, and with fewer all pay the payment vault. A payer that approves without limit returns false and gets the client's threshold of 3.

### What stays on the payment vault

External signers pay quotes one by one, so what they pay is quoted for the payment vault, at settlement version 2, whatever vault the client pays: prepared uploads (`file_prepare_upload`, `data_prepare_upload`) finished with `finalize_upload*`, prepared chunks (`prepare_chunk_payment`, `prepare_chunk_payment_plan`) finished with `finalize_chunk` or an external signer, a pointer's state quoted with `prepare_pointer_payment`, and the browser core.

### What stays

- Size classes, the band, the price ceiling, V2 occupied-quote handling, the merkle refusal, payment recovery, kept proofs and envelopes by default, with all five payment fields shown, are unchanged.
- Payment reads on the bundled network keep the order of v0.3.11+ds.6: PublicNode, then Robinhood's RPC, then ordofi last.

### Library users: ant-protocol from the same tag

As before, a project that uses `ant-core` takes both lines below, with the same tag:

```toml
[dependencies]
ant-core = { git = "https://github.com/Project-DSpace/darwin-client", tag = "v0.3.11+ds.7" }

[patch.crates-io]
ant-protocol = { git = "https://github.com/Project-DSpace/darwin-client", tag = "v0.3.11+ds.7" }
```

## Releases

- **It is tested against darwin-node 0.23.0+ds.20** (`363640e`), the revision its tests pin, which settles under version 3.
- **This release is published only after** the tagged commit's Test run and its Build run on `main` both passed.
- **Going back** to v0.3.11+ds.6 is a re-pin of both lines' tags under the usual pause; the CLI then pays the payment vault unless given `--root-payments`. An upload checkpoint holding a root payment is resumed by v0.3.11+ds.6 only with `--root-payments`, and can't be resumed by v0.3.11+ds.5.
